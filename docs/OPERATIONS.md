# Operaciones: despliegue y clave de administración
Léelo cuando toques Vercel, variables de entorno, veas un 401/503 en Admin/scrape/ingesta/entrenamiento, o vayas a compilar/publicar/instalar la app Android. Arquitectura general: [ARCHITECTURE.md](ARCHITECTURE.md).

## Estado actual (decisión consciente)
**El servidor ya no recibe escrituras de la web (#724).** Se retiraron la página Administración, `DELETE /collections/{name}`, `POST /scrape/*`, `POST /historical/ingest*` y el servicio `basketlab-scraper`: **cargar datos** es el refresco programado del archivo (*Archive refresh*, abajo) y **retirar una competición** es la purga (*Archive purge*). `ADMIN_API_KEY` **no está definida en producción**, a propósito, y solo protege lo que queda de escritura, el entrenamiento del predictivo (se conserva, fuera de la web mientras se rehace). Consecuencia con la API en producción (`ENVIRONMENT=production`; este repositorio no aloja ninguna, ver *Sin servidor alojado*):

| Funciona | Responde **503** ("ADMIN_API_KEY no está configurada en el servidor") |
|---|---|
| Todas las lecturas (equipos, jugadores, tiros, informes, rankings, rotaciones…) | `POST /api/v1/analysis/elasticity/train` y `/train/stream` (entrenar modelos) |
| Cómputo sin persistir: informe de equipo, export PDF, informe semanal, Monte Carlo, predicción de partido | |

El 503 es el comportamiento diseñado, no un fallo (`src/api/security.py`, probado en `tests/test_admin_auth.py`). En **local** (sin `ENVIRONMENT=production`) esas rutas están abiertas y no hace falta clave.

Para cargar o refrescar datos en local: `python run_archive.py pull` + `load` sobre un Mongo local y `python run_refresh.py --config config/competitions.json` contra él (ver *Refrescar el archivo sin Atlas*); ya no hay página ni ruta de servidor para ello.

## Sin servidor alojado (#334)
**BasketLab no depende de ninguna plataforma de alojamiento de la API ni se integra con ella** (Render se retiró del proyecto el 05/11/2026): no hay `render.yaml`, ni job de despliegue en CI, ni comprobación posterior, y `GET /api/v1/health` informa del commit solo si el entorno define `GIT_COMMIT`. La web publicada lee los ficheros de `web-data` (el valor por defecto desde #745) y la API (`python run_api.py`) sirve para desarrollo local, pruebas y el e2e. Quien aloje la API necesita las variables de abajo y `VITE_API_BASE` en la web para que su respaldo la use. **Fuera del repositorio** (a mano, GitHub → *Settings → Secrets and variables → Actions*): borrar el secreto `RENDER_DEPLOY_HOOK_URL` (y `RENDER_SCRAPER_DEPLOY_HOOK_URL`, si quedara) y la variable `RENDER_API_URL`.

## Activar la clave (paso a paso)
Hacerlo cuando se quiera usar Admin, scrape, ingesta o entrenamiento en producción.

1. **Generar una clave larga y aleatoria** (en cualquier terminal; no la pegues en el chat ni la commitees):
   - PowerShell: `[Convert]::ToBase64String((1..32 | ForEach-Object { Get-Random -Maximum 256 }))`
   - o Python: `python -c "import secrets; print(secrets.token_urlsafe(32))"`
   Guárdala en un gestor de contraseñas.
2. **Entorno del servidor de la API**: añadir `ADMIN_API_KEY` = la clave.
3. (El servicio `basketlab-scraper` se retiró en #724: solo la API tiene la clave; el frontend la envía en `X-Admin-Key`.)
4. **Reiniciar** el servicio para que lea la variable.
5. **Introducir la clave en la app**: la página Admin se retiró (#724); hoy solo la usa el entrenamiento del predictivo (`pages/predictive/ElasticityTab.tsx`, fuera de la web mientras se rehace), con el campo "Clave de administración" (`AdminKeyField`, `sessionStorage`). Si se reactiva el predictivo, se guarda ahí; por `curl` basta la cabecera `X-Admin-Key`.
6. **Comprobar** (sustituye URL y clave):
   ```bash
   # sin clave -> 401
   curl -i -X DELETE https://<api>/api/v1/collections/PRUEBA_INEXISTENTE
   # con clave -> pasa la guarda (404/200 según exista la colección, pero ya no 401/503)
   curl -i -X DELETE -H "X-Admin-Key: <clave>" https://<api>/api/v1/collections/PRUEBA_INEXISTENTE
   ```
   Cuidado: usa un nombre de colección que **no exista** al probar.

## Rotar o retirar la clave
- **Rotar**: cambiar el valor en el entorno del servidor, reiniciar y volver a guardarla donde se use. Las claves antiguas dejan de valer al instante (se lee en cada petición).
- **Retirar** (volver al estado actual): borrar la variable y reiniciar → vuelven los 503.

## Diagnóstico
| Síntoma | Causa | Solución |
|---|---|---|
| 503 "ADMIN_API_KEY no está configurada" | variable sin definir en ese servicio (producción) | Estado actual esperado; pasos de arriba para activarla |
| 401 "Clave de administración requerida o incorrecta" | sin clave en Admin, clave distinta | Re-guardar la clave en Admin |
| 503 "Base de datos no disponible: …" (o 500 en versiones antiguas) en cualquier endpoint con datos | `MONGODB_CONNECTION_STRING` sin definir, credenciales de Atlas rechazadas, usuario sin permisos o IP no permitida | Abrir `/api/v1/health/db`: `error` = `missing_config` / `auth_failed` / `not_authorized` / `unreachable` / `invalid_config` y `hint`. Revisar las variables de entorno del servicio y Atlas → Database Access / Network Access (`0.0.0.0/0` para Render free) |
| Atlas desactualizado respecto a local | el scrape se hizo solo contra la BD local | `GET /api/v1/collections/{name}/freshness` lista `missing_codes` (jugados en FEB y ausentes) |
| CORS / `OPTIONS` bloqueado | `ALLOWED_ORIGINS` no incluye la URL de Vercel | Ajustar `ALLOWED_ORIGINS` (la cabecera `X-Admin-Key` está permitida) |
| Funciona en local pero no en producción | en local no hay guarda (sin `ENVIRONMENT=production`) | Esperado |

## Variables de entorno (resumen)
Backend (si se aloja): `ENVIRONMENT=production`, `MONGODB_CONNECTION_STRING`, `ALLOWED_ORIGINS`, `ADMIN_API_KEY` (opcional hasta que se decida activarla). Frontend (Vercel): `VITE_API_BASE` (solo para el respaldo de la API). Plantilla: `.env.example`.

## Despliegue (web) y CI
La web se despliega sola en Vercel (integración nativa de GitHub, con una vista previa por PR). `ci.yml` solo ejecuta los tests (backend repartido en 4 trabajos, web, e2e); **no despliega nada**: los datos y los paquetes los publica GitHub Actions en las ramas `web-data` y `live-packages`. Si se aloja la API en algún sitio, el despliegue es cosa de quien la aloje (ver *Sin servidor alojado*).

## Comparar el archivo con Atlas (atlas-compare.yml, #724)
Antes de apagar Atlas hay que saber que **todo lo que tiene está en el archivo**. El workflow *Atlas compare* (a mano, y en los PR que lo tocan) restaura el archivo en un Mongo efímero, lee Atlas y deja en el resumen del run una tabla por colección: partidos en cada lado, ids que solo tiene Atlas, ids que solo tiene el archivo (las temporadas antiguas, esperable) y cuántos partidos no llevan el `DERIVED` actual. **Solo lee, en los dos lados**: Atlas se abre a través de `ReadOnly` (`src/local_data/atlas_compare.py`), que solo deja listar nombres y hacer `find` con proyección y lanza `PermissionError` ante cualquier otra operación, y el archivo no se sube. Sale en rojo si Atlas tiene partidos que el archivo no tiene. Al final añade un apartado informativo de `COLLECTION_META` (cuántos metadatos hay en cada lado, los de colecciones sin partidos y las colecciones con partidos sin metadatos): el archivo todavía no la lleva (paso 3 de #724) y no hace fallar el job.

**Credencial**: usa `ATLAS_READ_URI` si existe y, si no, `ATLAS_WRITE_URI` (como el resto de workflows). Atlas está deprecado (decisión del 03/11/2026), así que no se crea un usuario de solo lectura solo para esto: da igual lo que permita la credencial, el código solo lee (`ReadOnly`, con tests de que cualquier escritura lanza `PermissionError`). Si algún día se quisiera blindar también la credencial, bastaría un usuario con rol `read` y el secreto `ATLAS_READ_URI`.

## Rellenar `DERIVED` en partidos ya guardados (#372)
Los partidos que entran por el scrape (también el refresco del archivo) llevan `DERIVED` (posesiones exactas y rebotes/pérdidas validados) desde que se insertan. Los de FBCYL (`insert_fbcyl_match`, #373) también. **Cada refresco (el de Atlas y el local, `run_refresh.py`) rellena también `DERIVED` de las colecciones que toca** (#630: el local no lo hacía y dejó 167 partidos fuera de «Análisis pbp»; un fallo ahí nunca convierte el refresco en error) y **el workflow *Atlas refresh* lo vuelve a pasar a toda la base** (último paso, tras cada scrape, aunque el refresco salga en rojo; usa `ATLAS_WRITE_URI`; #382): idempotente, solo toca los partidos sin la versión actual; recorre todas las colecciones de partidos, así que su coste crece con el tamaño de la base (hoy despreciable; si llegara a pesar, indexar `DERIVED.v`). A mano, para los guardados antes o si sube `DERIVED_VERSION` (v2 en #352: puntos por origen; v3 en #353: periodos; v4 en #354 y #355: situaciones y tiempos muertos; v5 en #390: fiabilidad por impacto; v6 en #398: contraataque estimado (**sin la v5 los cuatro endpoints salen vacíos y sin la v6 `points-by-origin`**); **hasta rellenarlos `/possessions/{collection}/points-by-origin`, `/by-period`, `/situations` y `/timeouts` salen vacíos** (Atlas se rellena solo en el siguiente *Atlas refresh*)), se rellenan con `python run_backfill_derived.py [--collection NOMBRE]` (idempotente; solo añade el campo; deshacer: `updateMany({}, {$unset: {DERIVED: ""}})`). Contra Atlas: define `MONGODB_CONNECTION_STRING` en la sesión (PowerShell: `$env:MONGODB_CONNECTION_STRING = '…'`, comillas simples; usuario y contraseña con caracteres especiales codificados con `urllib.parse.quote_plus`; sin la variable usa `db_credentials.txt`, o sea la BD local). Sin `DERIVED` los pipelines usan el respaldo del boxscore. Alternativa si se vacía una colección: el workflow *Atlas refresh* (*Run workflow*) la recrea desde FEB con `DERIVED`.

## Refrescar el archivo sin Atlas (archive-refresh.yml, #724)
El workflow *Archive refresh* trae los partidos al día **sin Atlas** y es **el único que escribe el archivo privado**: 3 veces al día (05:30, 13:30 y 21:30 UTC) y a mano (*Run workflow*, con `only` para una primera carga pesada: `tercera feb`, `lf2`…) descarga el archivo de `<propietario>/basketlab-archive`, lo restaura en un `mongod` efímero (contenedor de servicio `mongo:7`), scrapea de FEB y de FBCYL lo que se jugó desde entonces (`run_refresh.py --config config/competitions.json`: las competiciones **activas** del catálogo, 3ª FEB con todos sus subgrupos; lo guardado se salta y los últimos días se revisan de nuevo, `recheck_days`), rellena `DERIVED` y guarda el archivo (`dump --no-shrink` y `push`: solo si cambió, un único commit y las últimas 10 versiones como etiquetas `archive-<fecha>-<sha>`). **Un partido «en juego» que FEB nunca cierra** (#724): el scrape salta los partidos con estado distinto de terminado (guardar uno a medias bloquearía el definitivo), pero un partido **no puede estar en juego 8 horas después de empezar**: pasadas 8 horas desde su inicio (`STALE_AFTER`) y con **los cuatro cuartos rellenos** en su marcador (`HEADER.QUARTERS.QUARTER`: `scoreA` y `scoreB` numéricos en al menos cuatro cuartos; una prórroga añade, nunca quita) se da por terminado y se guarda tal como FEB lo muestra, y un refresco de los últimos días lo sustituye si FEB lo corrige. Sin esto, el partido 2537218 de 3ª FEB B-B (jugado el 11-10-2026, aún «SCHEDULED» con los cuatro cuartos en FEB) se saltaba en cada refresco y dejaba el run en rojo siempre, ocultando los fallos de verdad (con el refresco de Atlas no se veía porque solo cubría el grupo A-B). Un scrape que informa de un problema (una competición falló o aún faltan partidos jugados) **no impide guardar** —los partidos nuevos valen la pena— pero deja el run **en rojo**, con el resumen. Necesita el secreto `ARCHIVE_DEPLOY_KEY` (clave de despliegue con escritura en el archivo). Dura unos minutos; el límite del job es de 90 min por una primera carga pesada (≈ 0,5 s por partido). Dos ejecuciones nunca corren a la vez ni se cancelan. **Por qué separado de la publicación**: `web-data` tarda de 45 a 60 min y el archivo se guarda con un commit forzado que sustituye al último, así que no puede tener un segundo escritor; y un refresco que espera detrás de una publicación larga es un refresco que se retrasa. *Archive refresh* corre en paralelo al *Atlas refresh* hasta que éste se retire; `web-data` espera ahora a *Archive refresh* y `live-packages` sigue esperando al de Atlas hasta el paso 4 de #724. Para traer partidos nuevos a mano: lanzar *Archive refresh* (publica después `web-data` solo).

## Purgar una competición del archivo (archive-purge.yml, #724)
Pausar una competición (`"active": false`) o quitar su entrada **no borra datos**, y el refresco se niega a reducir el archivo (`--no-shrink`); **la purga es la única orden que borra**, y es deliberada. *Actions → Archive purge → Run workflow*, **en dos pasos**: 1) con `competition` (la etiqueta del catálogo, p. ej. `PRIMERA FEB`; un grupo de FBCYL, la suya, `1ª FASE-GRUPO A-1` con `league` = `fbcyl`), `season` (`2024/2025`; FBCYL, `2026`) y **`confirm` vacío** es un **ensayo**: el resumen lista las colecciones, los partidos y el tamaño que borraría y no guarda nada; 2) repetirlo con `confirm` = la competición y la temporada **escritas exactamente** (`PRIMERA FEB 2024/2025`): cualquier otra cosa falla sin tocar nada. Reglas: una competición **activa** en el catálogo se rechaza (pausarla primero y dejar correr un refresco; si no, el siguiente la traería de vuelta); se borran todas las fases y grupos de esa competición y temporada (por el nombre de la colección: `COMPETICION_TEMPORADA_`, sin confundir `LF` con `LF CHALLENGE`), sus ficheros del archivo y sus metadatos (`COLLECTION_META`); no toca ninguna base de datos ni Atlas. El guardado deja las **últimas 10 versiones del archivo como etiquetas** (`archive-<fecha>-<sha>`): así se deshace un error (restaurar esa etiqueta). Comparte grupo de concurrencia con *Archive refresh* (una purga espera a un refresco y al revés) y *web-data* corre después y **retira lo purgado de la publicación** (es incremental: sin cambios es rápido). En local: `python run_archive.py purge --dir DIR --competition … --season … [--league fbcyl] [--confirm "…"]` sobre un archivo descargado con `pull`.

## Publicar los datos de la web (web-data.yml)
Tras cada refresco del archivo (*Archive refresh*, arriba), `web-data.yml` ejecuta `run_web_data.py` y publica en la rama `web-data` el manifiesto, las filas del contrato y los informes de equipo, sellados por alcance (ver [ARCHITECTURE.md](ARCHITECTURE.md), `src/local_data/web_data`; decisión de alojamiento en [la evaluación de #640](evaluaciones/2026-10-29_alojamiento-artefactos-640.md)). Parte de la rama anterior (para que lo que no cambió conserve sus bytes) y la reescribe con un único commit, **solo si algo cambió**. **Imágenes del DOCX (#717)**: cada publicación revisa el escudo y las fotos de los equipos de las competiciones de la temporada más reciente (un HEAD por imagen, ocho a la vez: unos 300 por competición) y solo baja las nuevas o las que cambiaron de tamaño; `--no-images` en `run_web_data.py` las omite. **Una competición que no ha cambiado no se recalcula (#700)**: `build-cache.json` (hashes, junto al manifiesto) guarda por competición la huella de sus filas y cifras derivadas y la versión del código (`src/` salvo `src/api`); con la misma huella y versión las secciones pesadas (partidos, posesiones, combinaciones, IN/OUT, rotaciones, tiros) reutilizan sus ficheros sellados. Un partido nuevo o corregido recalcula solo su competición; **un cambio de código recalcula todas** (la primera pasada tarda unos 50 min, de ahí `timeout-minutes: 120`; el log dice cuánto cuesta cada sección y cuáles se reutilizan, «reused»). Borrar `build-cache.json` fuerza el recálculo completo. Secretos: `ATLAS_READ_URI` (o `ATLAS_WRITE_URI`) y `PACKAGE_MASTER_KEY` (o `PACKAGE_PASSWORD`, ≥ 8 caracteres; los mismos de los paquetes live). Sin el secreto el run falla (código 2). **Mientras dure la beta** se envuelve también para el alcance `abierto` y el manifiesto publica su clave; cerrarla es `--closed` (y se corta rotando el alcance, como en los paquetes). **Lo lee la web (#639)**: con `?data=local` (se recuerda en el navegador; `?data=api` lo apaga) el *Informe de equipo* se abre en el navegador desde `raw.githubusercontent.com` (CORS abierto), sin servidor; `VITE_DATA_BASE` (Vercel) cambia el anfitrión. Mientras la beta esté abierta usa la clave abierta del manifiesto, sin pedir nada; con `--closed` la página pide una **invitación**: el enlace `https://<web>/#invite=bl1.<clave>` (la misma `bl1.…` que genera `src.live_prep.invite`) la guarda en ese navegador y la quita de la dirección. Una clave de club abre el análisis de su equipo y el scouting de todos; la de la competición, todo lo de ella. No hay revocación: el corte es rotar el alcance y republicar.

**Archivo privado y Mongo efímero (#646).** (Desde #724 el archivo lleva también `COLLECTION_META`: el efímero ya no empieza sin metadatos y los paquetes y las fases de `groups: all` no dependen de que el scrape de FEB responda.) Con el secreto `ARCHIVE_DEPLOY_KEY` el job deja de leer Atlas: descarga el archivo del repositorio privado `<propietario>/basketlab-archive`, lo restaura en un `mongod` efímero (contenedor de servicio `mongo:7`) y construye la web desde ahí. **Ya no scrapea ni guarda el archivo** (#724): eso lo hace *Archive refresh*, que corre antes y es el único que lo escribe. Sin el secreto lee Atlas como antes (3ª FEB solo A-B). **Scouting del rival publicado (#638)**: además de los informes, el job publica el scouting completo (`run_web_data.py`, `src/local_data/scouting_export`) de los equipos de las competiciones donde juega un club de interés (el del publicador y los `clubs` de `config/package_publish.json`; hoy 58 equipos: LF Challenge, 2ª FEB A y B y 3ª FEB A-B). **Medido con datos reales: 322 s para las cuatro competiciones, 114 ficheros (58 de liga, 28 de copa, 28 agrupados), 0,86 MB sellados y 7,3 KB cada uno**; 28 de los 58 equipos tienen partidos de Copa. Cada equipo tiene `liga`, y `copa` y `todo` si jugó la Copa; la página deja elegir qué ver (Liga por defecto, como Multifase). Ampliarlo a toda la temporada senior (~300 equipos, 50-70 min de cómputo) pide repartirlo en un job por competición en paralelo. **Límites**: sin comparativa con nuestro equipo (con «Nuestro equipo» elegido la página genera el informe en el servidor, como siempre) y sin PDF publicado (medido: 0,18 s y 38 KB por PDF de scouting, 0,10 s y 7 KB por PDF de informe; queda para un seguimiento corto porque exige sellado binario y su descarga). **Correcciones tardías de FEB**: el scrape incremental se salta los partidos que ya tiene, así que un partido que FEB corrige después se quedaba mal para siempre; `config/competitions.json` pide `"recheck_days": 3` en cada competición y el refresco **vuelve a descargar los partidos guardados de los últimos 3 días y sustituye por código de partido los que cambiaron** (`HEADER`, `BOXSCORE`, `PLAYBYPLAY` o `SHOTCHART`; mismo `_id`, `DERIVED` recalculado; nunca se borra: una descarga que falla, viene vacía o sin terminar deja lo guardado). El informe del refresco dice cuántos se revisaron y cuántos se corrigieron. `config/atlas_refresh.json` no lo pide (el refresco de producción no cambia). Comprobado contra FEB real: la descarga de un partido ya guardado es idéntica en las cuatro partes, así que no hay falsos cambios. Garantías: el archivo se guarda solo tras una restauración completa y **nunca con menos partidos** (`--no-shrink`: un restore a medias o una colección perdida detienen el job en rojo sin tocar nada); un archivo que cambió en el remoto desde la descarga no se sobrescribe. **Puesta en marcha (una vez)**: 1) repositorio **privado** vacío `basketlab-archive` (sin colaboradores: lleva los datos de FEB en bruto, #637); 2) sembrarlo desde la base local: `python run_archive.py dump --out ../basketlab-archive-seed`, `git init`, commit y `git push` (≈ 32 MB); 3) clave de despliegue: `ssh-keygen -t ed25519 -N "" -f <ruta fuera de cualquier repositorio>`, la pública en *Settings → Deploy keys* del repositorio privado **con escritura**, la privada como secreto `ARCHIVE_DEPLOY_KEY` de este repositorio (y borrar el fichero; desde PowerShell la clave llega con saltos CRLF o BOM y OpenSSH da `error in libcrypto`: el workflow la reconstruye a partir de su cuerpo base64 con `src/local_data/ssh_key` —acepta CRLF, BOM, NUL de UTF-16, espacios o `
` literales en vez de saltos, comillas y sin salto final— y la valida con `ssh-keygen -y`; si no es una clave, el error describe el texto (longitud, líneas, cabecera) sin repetirlo; lo más limpio es `gh secret set ARCHIVE_DEPLOY_KEY < fichero` desde Git Bash o pegarla en la web); 4) *Run workflow* de *Web data*. **Recuperar una versión anterior**: `git clone` del repositorio privado y `git checkout archive-<fecha>-<sha>` (o `python run_archive.py pull` y restaurar). **Límite**: las temporadas anteriores a la previa se guardan sin `PLAYBYPLAY`; recalcular `DERIVED` en ellas necesitaría el PBP (se rehace desde Atlas o desde la base local con `run_backfill_derived.py` y se vuelve a sembrar).

## Publicar los paquetes live (live-packages.yml)
**La descarga del archivo está escrita una sola vez (#732)**: la acción `.github/actions/restore-archive` (clave reconstruida y comprobada, `pull`, `load` e índice de equipo) la usan *Archive refresh*, *Web data*, *Live packages*, *Rule evaluation* y *Atlas compare*; *Archive purge* la usa con `restore: false` (solo descarga) y la deja lista para el `push` (`GIT_SSH_COMMAND` en `GITHUB_ENV`). Tras cada refresco del archivo (#724, paso 4: ya no tras el de Atlas), `live-packages.yml` construye los paquetes cifrados de los próximos partidos del club (`config/package_publish.json`) y los publica en la rama `live-packages` (un solo commit forzado, ver [LIVE.md](LIVE.md)). Los partidos salen **del archivo privado**: el job lo descarga y lo restaura en un Mongo efímero con la acción compartida `.github/actions/restore-archive` (solo lectura: nunca escribe el archivo; crea además el índice `HEADER.TEAM.id`, que un archivo no lleva y sin el cual cada partido de ~1 MB se recorre entero) y espera a *Archive refresh*, que lo guardó minutos antes. Puesta en marcha (una vez): secreto `PACKAGE_PASSWORD` (≥ 8 caracteres, el mismo que se escribe una vez en la app; el repo es público, usa una contraseña larga) y `ARCHIVE_DEPLOY_KEY`; sin esta, lee Atlas como antes (`ATLAS_READ_URI`, o `ATLAS_WRITE_URI` si no existe) hasta retirarlo (paso 5). **Una descarga o un restore que falla deja el run en rojo y los paquetes anteriores en la rama** (no se publica nada a medias). **Guarda de fases (#724)**: las fases de cada competición `groups: all` salen de `COLLECTION_META`; si una competición activa del catálogo se queda sin ninguna (`competitions_without_phases`), el publicador **para antes de escribir nada** (código 3, el run en rojo, sin índice que publicar) y la rama conserva los paquetes anteriores. Pasó de verdad: el primer refresco que sembró los metadatos en el archivo fue uno parcial (`only: tercera feb`) y los paquetes salieron con 3 rivales y las rondas de una sola competición en vez de 12 y las de ocho. **Por eso el primer *Archive refresh* tras sembrar los metadatos tiene que ser completo (sin `only`)**; las ejecuciones con `only` sirven para una carga pesada, no para sembrar. Si el workflow no se dispara tras el refresco, lanzarlo a mano (*Run workflow*). Además de los rivales del club publica la **jornada completa de cada competición** activa de `config/competitions.json` (`rounds/*.bpkgz`, ~70 KB por jornada y competición; `"rounds": false` en `config/package_publish.json` lo desactiva). El tiempo límite del job es de 60 minutos: cada competición cuesta una pasada por sus partidos (LF Challenge, ~14 s).

### Acceso a los partidos: abierto en la beta y clave después (#410)
`config/package_publish.json` → `access` decide cómo se cifra lo que se publica:
- `mode: "legacy"` (**por defecto hoy**): contraseña `PACKAGE_PASSWORD`, índice v1; es lo que leen las apps ya instaladas.
- `mode: "scoped"`: cada paquete lleva su propia clave aleatoria, envuelta una vez por **alcance** (`abierto`, `club:<id>`, `competicion:<colección>`, más los de `access.scopes` —p. ej. `temporada:2026-27`— y `mensual:<AAAA-MM>` con `monthly: true`). Las claves de los alcances salen de un secreto maestro (`PACKAGE_MASTER_KEY`; si no existe se usa `PACKAGE_PASSWORD`, sin secreto nuevo). El índice es v2: con `open: true` publica la clave del alcance `abierto` y **la app abre los partidos sin contraseña ni enlace**; las claves de pago no se publican.

**Puesta en marcha (una vez, tras la release de la app que lee alcances)**: la app actual **no lee el índice v2** («Actualiza la app»), así que el orden es 1) release del viernes con la app nueva y los beta actualizados con el botón de la app, 2) PR de una línea que pone `"mode": "scoped"` (con `"open": true`), 3) *Run workflow* de *Live packages*. Los paquetes con contraseña antiguos se siguen leyendo.

**Activar la clave** (cerrar la beta): poner `"open": false` y volver a publicar. Los paquetes nuevos ya no se envuelven con `abierto` ni se publica su clave; **no se recifra nada** (las claves envueltas viven en el índice, no en el fichero). A quien deba conservar el acceso se le da una invitación: `PACKAGE_MASTER_KEY=… python -m src.live_prep.invite --scope club:1008631 [--scope temporada:2026-27] [--expires 2027-06-30]` imprime el **enlace** `basketlab-live://invite#<clave>` (al tocarlo, la app se abre y guarda el acceso) y la **clave** suelta (*Partidos → Invitación → Usar invitación*). Quien tenga la clave de un alcance abre sus paquetes: se envía solo a quien deba tenerla.
**Caducidad**: un dispositivo sin servidor no puede imponerla; `--expires` solo hace que la app deje de usar la clave ese día. El corte real es rotar el alcance (`mensual:2026-12`, `temporada:2027-28`): los paquetes nuevos se envuelven con la clave nueva y la antigua deja de abrirlos. **Límites asumidos**: no se revoca lo ya descargado, y el historial de la rama pública `live-packages` conserva los índices antiguos con la clave abierta (si importara, reescribir la rama al activar la clave).

## Dependencias y seguridad (#525)
- **Dependabot** (`.github/dependabot.yml`): cada lunes abre, agrupados por ecosistema (menores y parches; los cambios mayores se hacen a propósito), los PR de `frontend/`, `apps/live-android/` y GitHub Actions (menores y parches, con `rebase-strategy: disabled`: una rama no se rebasa cada vez que avanza `main`, que repetiría todo el CI; pídelo con `@dependabot rebase` cuando vayas a integrarla). **pip no abre PR de versiones** (`requirements.txt` usa rangos `>=` y el CI y Render ya instalan lo último: solo subiría una cota mínima); sí llegan sus avisos de seguridad, que además se comprueban con `pip-audit -r requirements.txt` (23/10/2026: sin vulnerabilidades). Los avisos de seguridad llegan también como PR aparte en cualquier momento. `pyodide` está **fijado** en la app (el motor de la tablet y los vectores se miden con esa versión): cambiarlo es una decisión, con `npm run test:run` y `e2e` de la app. Un PR de Dependabot se integra como los demás (CI en verde).
- **Comprobar a mano**: `cd frontend && npm audit --omit=dev` (la app live: `cd apps/live-android && npm audit --omit=dev`). Estado del 23/10/2026: la app live sin avisos; el frontend sin avisos (0 vulnerabilidades) tras subir `jspdf` (crítico), `axios`, `dompurify`, `lodash`, `form-data` y `react-router-dom` a la 7 (#526). Con una vulnerabilidad `high` o `critical` en producción se actualiza ya, sin esperar a Dependabot.

## Memoria (servidor pequeño, 512 MB)
Un documento de partido pesa ≈ 1 MB en memoria de Python y la app completa ≈ 170 MB en reposo (más: scikit-learn +125 MB al primer uso predictivo, matplotlib +45, pandas +50). Medidas tomadas (issue #163), vigentes si alguien aloja la API en un servidor con poca RAM:
- **Un solo worker** de uvicorn por defecto (`src/api/runtime.uvicorn_workers`; `WEB_CONCURRENCY` lo sube, tope 4). Antes `run_api.py` lanzaba 4 en Linux → ~500-700 MB en reposo y OOM intermitente al desplegar.
- `MALLOC_ARENA_MAX=2` (menos fragmentación) y `pip install --no-cache-dir` al instalar.
- Listado de partidos con **proyección** (no cargar documentos completos), zonas de liga **en streaming** y caducidad (15 min) de los ZIP del informe semanal sin descargar.
- **Diagnóstico**: poner `LOG_MEMORY=1` en el servicio; los logs mostrarán `WARNING basketlab.memory GET /ruta rss 412 MB (+90 MB)` para peticiones que suben ≥ 25 MB (`LOG_MEMORY_DELTA_MB`) o dejan el RSS ≥ 350 MB (`LOG_MEMORY_HIGH_MB`).
- Regla de código: nunca `find({})` sin proyección sobre colecciones de partidos; iterar cursores/generadores en vez de materializar listas de documentos o tiros.
Si aun así se supera el límite: más memoria o separar los endpoints predictivos (scikit-learn) en otro servicio.

## App Android (BasketLab Live): APK, firma y publicación
La app (`apps/live-android`) se compila **en GitHub Actions** (`.github/workflows/live-android.yml`); no hace falta Android Studio ni Java en local. Cada PR/push que toque la app deja el APK como artefacto del workflow (requiere sesión de GitHub para descargarlo). Para tener un **enlace directo** (el repo es público) se publica una Release con una etiqueta.

### Publicar una versión
```bash
git tag live-android-v0.1.0
git push origin live-android-v0.1.0
```
El workflow compila, firma y publica **dos** releases:
- **Por versión** (histórico): `https://github.com/kanijoman/BasketLab/releases/tag/live-android-v0.1.0`, con `basketlab-live-0.1.0.apk`. Ambas se publican como *prerelease*: así nunca son la "latest" del repo (`make_latest:false` no basta: GitHub elegiría la más reciente).
- **Enlace fijo a la última** (`live-android-latest`, se recrea en cada etiqueta): `https://github.com/kanijoman/BasketLab/releases/download/live-android-latest/basketlab-live.apk`. Es el que conviene guardar en el móvil/tablet.
No uses `releases/latest` para la app: apunta a la última release **de todo el repo** (hoy solo hay releases del APK, pero si se publicara otra cosa dejaría de servir). Convención: etiquetas `live-android-vX.Y.Z` para el APK (y `web-v*` si algún día hay releases de la web); listado solo del APK: `https://github.com/kanijoman/BasketLab/releases?q=live-android`. El `versionCode` sube solo (número de ejecución del workflow), así que cada APK puede instalarse **encima** del anterior.

### Ciclo de publicación: cada viernes por la mañana
Decisión del 13/10: **cada viernes por la mañana** se publica una versión con todo lo integrado hasta ese momento (puede haber partidos el viernes por la tarde o noche, así que no más tarde) y el staff se actualiza con el **botón de la propia app** (*Actualizar* en el aviso superior o *Buscar actualización* en *Acerca de*). La versión sube el número menor (0.2.0 → 0.3.0 → 0.4.0…). Con cada versión el workflow sube además `latest.json` a la release fija `live-android-latest`: es lo que lee la app para saber si hay una más nueva (ver [LIVE.md](LIVE.md)).
**Publicación automática (#279)**: el workflow `live-android-release.yml` se ejecuta **los viernes a las 07:00 UTC** (las 09:00 en Madrid con horario de verano, las 08:00 en invierno) y decide con `scripts/live_android_release.py` (con tests):
- **¿Hay algo que publicar?** Compara con la última etiqueta `live-android-v*` (la de mayor versión, no la más reciente) y solo cuentan los cambios que acaban en el APK: `apps/live-android`, `src/live_core`, `design`, `tests/live_vectors`, `tests/recordings` y `src/JSON_samples/feb_game.json`, **sin** documentos ni tests. Sin cambios no publica nada y lo dice en el resumen del run.
- **Versión**: la última + 1 en el número menor. A mano (*Actions → Live Android release → Run workflow*): `version` (X.Y.Z, posterior a la última) fuerza otra, `force` publica aunque no haya cambios y **`dry_run`** enseña la versión y las notas que se publicarían **sin publicar nada** (para ensayar).
- **Notas**: los títulos de los PR integrados desde la anterior (`generate-notes` de la API de releases), completos en la release y resumidos (hasta 8 y 600 caracteres) en el `latest.json` que muestra la app.
- **Cómo publica**: una etiqueta creada con el `GITHUB_TOKEN` **no dispara otros workflows**, así que no etiqueta: lanza `live-android.yml` con la versión y las notas (`workflow_dispatch`). Ese workflow pasa sus tests, compila **desde `main`** (solo `main`: desde otra rama falla), firma con la clave de la release y crea la etiqueta y las dos releases (por versión y `live-android-latest`). El `versionCode` sigue siendo el número de ejecución de `live-android.yml`, que solo crece (uno menor haría que Android rechazara la actualización).
- Empujar una etiqueta `live-android-vX.Y.Z` a mano sigue funcionando como antes. Si algo falla (tests rojos, firma), el run de `live-android.yml` lo dice y no se publica nada; se corrige y se vuelve a lanzar a mano.

**La primera vez** (la versión que trae el botón, la 0.3.0): la 0.2.0 instalada no sabe actualizarse, así que se instala a mano como abajo; las siguientes, con el botón. Android siempre pide confirmar la instalación y, la primera vez, permitir apps desconocidas.

### Instalar en el móvil / tablet (una vez por dispositivo)
1. Abrir el enlace de la Release en el navegador del dispositivo y descargar el `.apk`.
2. Android pedirá permitir **"Instalar apps desconocidas"** para ese navegador (o gestor de archivos): *Ajustes → Apps → [navegador] → Instalar apps desconocidas → Permitir*. No hace falta modo desarrollador ni depuración USB.
3. Abrir el APK y pulsar *Instalar*. Si Play Protect avisa de "app no verificada", elegir *Instalar de todos modos*.
4. Actualizar = descargar el APK nuevo e instalarlo encima (misma clave de firma, `versionCode` mayor). Si el dispositivo es de un MDM del club, puede tener bloqueadas las fuentes desconocidas.

### Clave de firma propia (recomendado antes de la primera tablet "de verdad")
Sin los secretos de abajo el workflow firma con una clave de depuración **efímera**: el APK se instala, pero el siguiente build no podrá actualizarlo (habría que desinstalar la app y se pierden sus datos). Con la clave propia, todas las versiones son actualizaciones válidas.
1. Generar el almacén (necesita un JDK; `keytool` viene con él, p. ej. `winget install Microsoft.OpenJDK.21`):
   ```bash
   keytool -genkeypair -v -keystore basketlab-release.keystore -alias basketlab -keyalg RSA -keysize 2048 -validity 10000
   ```
   Anota las contraseñas. **Guarda una copia del `.keystore` y las contraseñas en un sitio seguro: si se pierden no se podrá actualizar la app instalada.** No lo commitees (`*.keystore` está en `.gitignore`).
2. Codificarlo en base64 (PowerShell): `[Convert]::ToBase64String([IO.File]::ReadAllBytes("basketlab-release.keystore")) | Set-Clipboard`
3. GitHub → *Settings → Secrets and variables → Actions → New repository secret*, cuatro secretos:
   `ANDROID_KEYSTORE_BASE64` (el base64), `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS` (`basketlab`), `ANDROID_KEY_PASSWORD`.
4. Publicar una versión nueva (etiqueta). Si ya había una app instalada con la clave efímera: desinstalarla una vez.
Rotar la clave implica desinstalar y reinstalar en todos los dispositivos.
